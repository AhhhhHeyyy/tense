# 候選連結產生器與修正紀錄機制 規格

> 狀態：草案，待坑主／事件線編輯複核。本文件性質同共筆〈spec/〉——規格文件，不含最終程式碼，落地前應可被檢視、被質疑。
> 前置閱讀：`時態計畫_g0v線上提案共筆.md`、`資料分流企劃案.pdf`（若無法取得 PDF，本文件已把相關條款摘錄在下方）。

## 0. 這個機制解決什麼問題，不解決什麼問題

**解決的問題**：三把自動串線鑰匙（提案編號／法律編號／會議代碼）處理不到的「跨案議題」，目前完全靠事件線編輯人工搜尋、人工判斷（共筆語：「只有極少數橫跨多法案的大議題需要人判斷」）。這件事本身沒有留下紀錄，每次都是從零開始判斷。這個機制的目標是：**把人工判斷的結果留下可稽核的紀錄，並用這份紀錄產生「值得優先看」的候選清單，降低事件線編輯搜尋題目的成本**。

**不解決的問題**：這個機制不負責「決定要不要開一條新線」——那永遠是 1.4 節既有的人工流程（提案人寫理由→事件線編輯查重複→顧問掃文案）。

## 1. 硬性排除（不可違反，違反視為規格不符）

以下是這幾輪討論過程中明確評估並駁回的做法，任何實作都不能引入：

1. **不做社群公開投票**。候選清單只給事件線編輯／坑主看，不對外開放 upvote/downvote，不設「票數達標自動發布」的機制。理由：立法程序判斷需要專業門檻（1.1 節法律案/預算案時程差異），公開投票容易被動員操縱，也架空既有的把關流程。
2. **候選分數不對外呈現、不包裝成機率**。任何相似度分數只用於「排序該優先看誰」，不呈現「88% 機率」這種語句給終端讀者看，避免製造假精確感。
3. **不自動發布**。候選清單通過門檻只代表「值得事件線編輯花時間看」，發布仍要走完整的 1.4 節三步流程，沒有任何自動觸發發布的路徑。
4. **不計算跨線的聚合效率統計**。這個機制的比對維度只用來判斷「是不是同一議題」，絕不能延伸出「這個委員會平均審多久」「這條線比平均慢幾天」這類聚合統計並顯示出來——直接對應企劃案 2.4 節禁止清單：「不計算『平均耗時』之類的聚合統計去暗示效率高低」。
5. **不對全體新增議案地毯式掃描**。掃描範圍限定在「已追蹤中的線的鄰域」（見第 3 節），不是每天把所有新進議案拿去互相比對找可能的新議題——那是完全不同、成本高得多的問題，不在這個機制範圍內。

## 2. 資料結構

### 2.1 `data/link_corrections.jsonl`（append-only，git 追蹤）

每行一筆 JSON，記錄一次人工判斷：

```json
{
  "date": "2026-08-24",
  "bill_a": "202110228820000",
  "bill_b": "202010119990000",
  "decision": "confirmed_same_line",
  "reason": "同一部就服法第55條修正，五組人各自提案",
  "decided_by": "事件線編輯",
  "candidate_score": 0.81,
  "matched_signals": ["法律編號相同", "對照表法條重疊"]
}
```

- `decision` 只允許三種值：`confirmed_same_line` / `confirmed_different_line` / `rejected_noise`（假陽性，連判斷都不值得，純粹是產生器抓錯）。
- 冷啟動：實作時先手動回填現有兩條 demo 線（食安修法線、軍購特別預算線）的串接理由，不用等新案例才有第一筆資料。
- 這個檔案本身即使沒有任何自動化，也有獨立價值：把原本只存在編輯腦中的判斷變成可稽核紀錄，直接對應共筆「可重現率」指標。

### 2.2 `data/link_heuristic_weights.json`（人工可讀、可調）

```json
{
  "對照表法條重疊": 0.4,
  "法律編號重疊": 0.35,
  "提案人或連署人重疊": 0.1,
  "委員會相同": 0.1,
  "議案名稱字詞重疊": 0.05
}
```

- 權重總和不強制為 1，只是相對排序用。
- **刻意不用 embedding／LLM 相似度分數取代這張表**：這張表任何人都能讀懂「為什麼這兩案被判定可能相關」，可以直接寫進未來的選線判准頁（企劃案 2.2 節），黑盒模型分數做不到這件事。
- `對照表法條重疊`（見第 4 節）權重最高，因為它是結構化欄位比對，不是模糊語意匹配，可信度遠高於標題關鍵字重疊。

## 3. `scripts/suggest_links.py`（新增腳本）

### 3.1 掃描範圍（硬性限定）

只對以下候選對做比對，不做全量掃描：

- 已追蹤中的每條線的 `seed_bill_no`，透過 `/v2/bills/{id}/related_bills` 或 `/v2/law/{法律編號}/bills` 找到的關聯案，且**這些關聯案尚未被納入任何現有線**。
- 已追蹤中的線，若判斷可能跨屆（`term` 有變化、`related_bills` 查無結果但法律編號相同）時的候選承接案。

不掃描與現有線完全無關的新進議案——那屬於「發現全新議題」的範疇，是 1.3 節選題研究的工作，不是這支腳本的責任。

### 3.2 比對維度與資料來源

| 維度 | 資料來源 | 說明 |
|---|---|---|
| 對照表法條重疊 | `/v2/bills/{id}` 的 `data.對照表.rows` | 已於 2026-08-24 實際打 API 驗證存在此欄位。比對 `law_id` 是否相同、`rows` 裡改的是否為同一批條號。這是目前找到最可靠的結構化訊號。 |
| 法律編號重疊 | `data.法律編號` | 沿用現有 `fetch_lyapi.py` 已抓的欄位。 |
| 提案人或連署人重疊 | `data.提案人`／`data.連署人` | 沿用現有欄位，計算交集比例。 |
| 委員會相同 | 議案流程階段裡的委員會資訊，若欄位不存在需另外確認 API 是否提供 | 待實作時查證，若查無此欄位則此維度先不做，不要用猜測值頂替。 |
| 議案名稱字詞重疊 | `data.議案名稱` | 權重最低，因為共筆已驗證過 LYAPI 中文檢索是字元級模糊比對，容易誤判（「解凍」配到「解釋」），這個維度只能當輔助分數，不能單獨決定候選是否入列。 |

### 3.3 輸出

`data/link_candidates.json`，格式：

```json
[
  {
    "bill_a": "...", "bill_b": "...",
    "score": 0.76,
    "matched_signals": ["對照表法條重疊", "法律編號重疊"],
    "generated_at": "2026-08-24T07:00:00"
  }
]
```

- 只列出分數最高的前 N 筆（見第 5 節熔斷機制的上限），不是全部候選都列。
- 這份檔案不直接餵進 `build_data.py` 或任何發布流程，只是給人看的候選清單。

## 4. 迭代機制（人工調權重，不做自動訓練）

**第一階段（現在就能做）**：不做任何自動學習。每季（比照共筆自訂的維護節奏）由坑主或事件線編輯檢視 `link_corrections.jsonl`，人工判斷哪個維度常常誤導，手動改 `link_heuristic_weights.json` 裡的數字，用一般 PR/commit 提交，commit message 寫清楚為什麼調整。

**第二階段（有明確前提才考慮，不是預設要做）**：只有當 `link_corrections.jsonl` 累積到有意義的量（抓 50～100 筆當量級參考，不是精確門檻）時，才評估是否值得寫一支簡單的邏輯回歸（scikit-learn，GitHub Actions 裡 CPU 秒級可跑完，不需要 GPU 或常駐服務）取代手動調權重。即使做到這步，**擬合出來的係數也必須印出來、寫進判准頁**，不能只留在模型檔案裡變成黑盒。這個階段完全可以不做，不影響第一階段的價值。

## 5. 熔斷機制（不可省略）

這個機制的迭代上限取決於人工複核候選清單的速度，而事件線編輯的時間是整個專案最稀缺的資源。**不設熔斷等於預設「待審清單會無限累積」，這比不做這個機制還糟**——一個沒人處理的候選清單本身會變成新的技術債，製造「這裡有事沒人管」的觀感。三個必要限制：

1. **候選隊列上限**：`link_candidates.json` 只保留分數最高的前 N 筆（建議先設 N=10，實作時可調），其餘直接丟棄，不進入任何形式的累積佇列。
2. **backlog 逾期自動暫停**：若連續 M 週（建議 M=6，對齊共筆「連續 90 天沒人回應」死亡條款的量級）候選清單沒有任何一筆被標記處理（即 `link_corrections.jsonl` 沒有新增），`suggest_links.py` 下次執行時自動輸出空清單並在 `data/link_suggester_state.json` 寫入 `{"status": "paused", "paused_since": "..."}`，退回純三把鑰匙的既有機制。
3. **狀態必須可見，不能靜默**：`link_suggester_state.json` 的狀態要在議題目錄頁（若已上線）或至少在 README 標示，任何人都能查到這個機制目前是啟用還是暫停，不能是只有看程式碼才知道的隱藏狀態。

## 6. 實作前必須先驗證的事（不要假設）

1. **LYAPI 清單端點篩選是否已修復**——`fetch_lyapi.py` 開頭記錄 2026-08-07 時完全失效，實作前重新打一次確認現況，這會影響能不能用篩選查詢輔助掃描範圍。
2. **委員會欄位是否存在於 `/v2/bills/{id}` 或 `/v2/meets/{id}`**——目前只在 `fetch_meeting.py` 抓到的 `委員會代號:str`（來自 `/v2/meets`），`/v2/bills` 端點是否也有對應欄位待查證，不要假設兩者欄位一致。
3. **`對照表` 欄位的穩定性**——只驗證過一筆議案（`202110228820000`），實作前應多抓幾筆不同類型的議案（尤其預算案，1.1 節提到預算案審查邏輯跟法律案不同，`對照表` 欄位是否同樣適用於預算案需要另外確認）。

## 7. 驗收標準

- [ ] `link_corrections.jsonl` 存在，且已回填至少 2 條現有 demo 線的串接理由
- [ ] `suggest_links.py` 能對指定的追蹤中線跑出候選清單，且候選只來自第 3.1 節限定的掃描範圍（不做全量掃描）
- [ ] 候選清單不含任何自動發布路徑，人工確認/駁回後才寫回修正紀錄
- [ ] 熔斷機制三項（隊列上限、逾期暫停、狀態可見）都已實作，且有對應測試或手動驗證步驟
- [ ] 沒有任何聚合效率統計（平均耗時、排名）出現在候選清單或任何面向讀者的輸出
