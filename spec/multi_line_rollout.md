# 資料分流：多線功能落地總覽

> 狀態：草案，整合〈資料分流企劃案〉〈資料分流使用者地圖〉與後續多輪可行性評估的結論。本文件是給實作者（含未來接手的新對話/新協作者）看的執行藍圖，不是決策文件——所有標「待坑主/事件線編輯複核」的項目都還沒最終拍板。
> 配套文件：`spec/candidate_linker.md`（候選連結產生器子模組）、`時態計畫_g0v線上提案共筆.md`（專案根本原則，任何實作前必讀）。

## 0. 為什麼要做這個

現行原型一次只掛一條事件線，法案類型／提案來源等分類欄位因此永遠同質（示範線食安修法 11 個法案的議案類別／提案來源全部相同，篩選器形同虛設）。這是單線資料的結構性侷限。解法是同時追蹤 2～3 條線，但**不能繞過共筆已經寫死的規矩**——見第 1 節。

## 1. 治理紅線總覽（所有 Phase 都不能違反）

這些是這幾輪討論中反覆確認、且分散在共筆與企劃案各處的規矩，集中列在這裡避免遺漏：

| 紅線 | 出處 | 白話 |
|---|---|---|
| 不判定真假 | 共筆〈刻意不做的六件事〉 | 不查核訊息真偽 |
| 不打分數排名 | 共筆、企劃案 00 節 | 不對法案/立委/委員會評分排序 |
| 不做個人化推薦 | 共筆、企劃案 3.5 節 | 系統不依使用者歷史自動決定顯示什麼；記憶只能用於使用者自己明確設定過的介面偏好（如白話/專業模式切換），不能用於推薦內容 |
| 不計算聚合效率統計 | 企劃案 2.4 節禁止清單 | 不算「平均耗時」之類的統計去暗示誰快誰慢，即使是議題層級（非個人層級）的統計也不行 |
| 不用進度條比較完成度、不做可排序的委員姓名欄位 | 企劃案 2.4 節禁止清單 | 同上精神的具體呈現限制 |
| 線色只做標籤不做色塊 | 企劃案 3.3 節 | 避免大面積色塊被誤讀成重要性/完成度 |
| 同時最多 3 條線，第 4 條起強制灰階「其他」 | 企劃案 3.3 節 | 色票驗證過的安全並列上限 |
| 選線要走三步人工流程，不能自動發布 | 企劃案 1.4 節 | 提案人寫理由→事件線編輯查重複→顧問掃文案 |
| 分類欄位有法定意義，不能被語意相似的「主題標籤」取代 | 企劃案 1.1 節 | 法律案/預算案審查路徑不同，不能因為關鍵字聚類混進同一條時間軸 |

## 2. 現有程式碼現況（實作前先確認未過時）

- `scripts/fetch_lyapi.py`：抓單一議案線，已支援 `related_bills` 展開。清單端點篩選（提案編號/法律編號/議案狀態查詢）**截至 2026-08-07 完全失效**，實作前重新驗證是否已修復。
- `scripts/fetch_meeting.py`：以會議代碼為錨點抓聯席會議節點，用於議案編號查不到關聯的案子（如軍購特別預算案）。
- `scripts/build_data.py`：目前 `--line` 參數只吃單一線 JSON。`build_legislative_row()` 內部 `row[d]` 已經用 list 存節點（見 [build_data.py:110-118](../scripts/build_data.py#L110-L118)），合併多線本質上是幫節點多標 `line_id` 再合併字典，不用重寫資料結構。
- `.github/workflows/daily-refresh.yml`：純靜態站台，每日 cron 呼叫 `refresh_data.py`，有變動才 commit。**沒有常駐後端或資料庫**——任何新機制都要能塞進「跑一次腳本、產出 JSON、git commit」這個模式，不能假設有常駐服務。
- 已用 `/v2/bills/{id}` 實際驗證（2026-08-24）：有結構化的 `對照表.rows`（條文對照）、`提案人`/`連署人`/`案由`/`說明`；**沒有**表決結果（贊成/反對名單、票數）欄位。`/v2/meets/{id}` 也**沒有**逐字稿或 IVOD 連結欄位——這兩塊如果未來要做，需要接全新資料源，不是現有腳本能擴充的範圍，本次 Phase 1-3 不含這塊。
- `term`（屆別）欄位已在抓（[fetch_lyapi.py:76](../scripts/fetch_lyapi.py#L76)），但文件記錄常回傳 null，實作 Phase 1 前應先排查是資料源缺口還是解析邏輯問題。

## 3. Phase 0：已完成

兩條線（食安修法線、軍購特別預算線），只能透過 `?data=` 擇一顯示，無法同框比較。

## 4. Phase 1：合併 2 條線 + 前端過渡原型（建議下一步，工程量小）

**目標**：驗證「使用者到底看不看得懂『多線』這個概念」，不等目錄頁做完。

**範圍**：
1. `build_data.py`：`--line` 改為可接受多個路徑或一份清單檔（`data/lines/*.json`），迴圈處理，每個節點標上 `line_id`，合併進同一天的 `nodes` list。**這是純資料層改動，不影響行政／搜尋次數／媒體報導三列**。
2. 前端：採用企劃案 3.2 節「方案 B」——同一天格子內卡片依線分組，每條線一個小色點＋文字標籤，不佔用既有列色版位。沿用現有卡片元件。**不做方案 C（獨立議題泳道）**，那是 Phase 3 的事。
3. `term` 欄位擷取邏輯排查與修正（見第 2 節）。
4. （建議一併做，非必要但降低後續選題成本）`spec/candidate_linker.md` 描述的候選產生器最小版本——`link_corrections.jsonl` 建檔並回填現有兩條線的串接理由。這部分獨立於前三項，可平行進行。

**選第三條線的題目限制**（企劃案 1.3 節判準，避免同質化）：
- 至少要有 1 條「黨團提案」案例（現況缺口，兩條 demo 線都沒有，需另尋題目）
- 政策領域要跟食安、國防預算都不同
- 這是純人工搜尋工作，沒有固定工時，`suggest_links.py` 不負責發現全新議題（見 `spec/candidate_linker.md` 3.1 節），這裡只能靠人工盤點

**Phase 1 驗收標準**：
- [ ] `build_data.py` 能吃 2 條線的清單檔，輸出的 `events.json` 立法列每格可能同時出現來自不同 `line_id` 的節點
- [ ] 前端方案 B 上線，色標籤在截圖後仍可辨識（呼應使用者地圖「記者」畫像的設計提醒）
- [ ] `term` 欄位不再固定回傳 null（或已確認是資料源本身的缺口並記錄下來）

## 5. Phase 2：議題目錄頁 + 選線判准公開文件

**目標**：讓「選線是一種編輯權力」這件事變成可被檢視、可被複製的治理流程，不只是坑主腦中的標準。

**範圍**：
1. 新增議題目錄頁：每條線顯示主題名稱、追蹤中的法案數、日期範圍、分類分佈快照（如「3 法律案·1 預算案」）、最後更新時間、選線判准的連結。
2. 選線判准比照共筆 `clock_anchor` 先例，寫成獨立公開文件，**投給整個開放國會社群共用，不掛在本專案名下**——這一步是社群協調，時間不完全可控，不要排進硬性工期。
3. 分類標籤白話／專業雙模式並存（企劃案 2.5 節），這是多線化後被放大的既有難題，不能延後。
4. 加開的線要能完整編碼進網址（如 `?lines=food-safety,military-budget`），維持可分享／可引用（使用者地圖裡 NGO 研究員、研究生兩種畫像的核心需求）。

**Phase 2 驗收標準**：
- [x] **2026-08-29**：議題目錄頁已上線（`scripts/build_catalog.py` 產出 `data/catalog.json`，`index.html` 的 `renderCatalog()` 讀取後畫卡片，取代原本三個純文字連結）。每張卡片顯示主題名稱、追蹤中議案數、日期範圍、分類分佈快照、最後更新時間。**但「選線判准說明」目前只連回本 repo 的 `spec/multi_line_rollout.md`**，不是下面第 2 項要求的獨立公開文件——那份文件還沒寫、也還沒投給社群，卡片上誠實註明了這點，沒有假裝已經完成。已接進 `refresh_data.py`，每日重跑不會跟 `events.json` 脫鉤。
- [ ] URL 參數完整編碼目前顯示的線組合（`?lines=food-safety,military-budget` 這種任意組合）——**尚未做**。目前架構是靠 `build_data.py` 在 build time 把固定組合預先合併成三份靜態 `events*.json`，`?data=` 只能三選一，不是任意勾選 2～3 條線再即時合併。要做到任意組合需要前端在 runtime 重現 `build_legislative_row()` 的合併邏輯（改吃每條線各自的原始節點檔，不是預先合併好的 `events*.json`），工程量比目錄頁大一截，這次沒有一併做。
- [ ] 白話／專業雙模式切換存在且記憶使用者上次選擇——**尚未實作**。`spec/reading_mode_onboarding.md` 已起草機制設計，但預設模式（第 4 節）跟對話文案的法律用語審閱（第 5 節）都還沒拍板，貿然刻文案風險最高的部分不該由工程單方面決定，見該文件。

## 6. Phase 3：獨立議題泳道（視 Phase 1 驗證結果決定，不預先承諾）

方案 C：使用者從議題目錄勾選 2～3 條線，畫面新增獨立列，每條線一列，不塞進既有立法列。Grid 列數要從固定 4 列改成動態，企劃案自估「工程量最大」。**只有 Phase 1 驗證出「使用者理解多線」且有實際需求時才啟動**，不是既定要做的項目。

## 7. 附錄：討論過程中評估並駁回的方案（避免重新踩坑）

新的協作者/新對話如果重新提出以下方向，可以直接參考這裡的駁回理由，不用重新논證一次：

### A. LLM 預比對 + Cofacts 式社群協作看板（三階段管線：LLM 生成候選→開放投票→編輯快速勾選）
**駁回理由**：Upvote/Downvote 本質是排名機制，且「這兩案算不算同一議題」需要 1.1 節的專業判斷，開放公眾投票容易被動員操縱；「投票達標即推播、編輯快速勾選同意」把 1.4 節設計成有實質內容的把關流程做虛了；相似度分數包裝成「88% 機率」製造假精確感，牴觸「不判定真假」原則。**保留的部分**：LLM/規則式候選產生器當「輔助發現工具」是可以的，即 `spec/candidate_linker.md` 現在的設計，但不涉及公開投票、不自動發布。

### B. 根據官方文件關鍵字提取自動分配議題
**駁回理由（技術面）**：實測 `fetch_lyapi.py` 清單端點篩選當時完全失效，關鍵字查詢在立法資料上連起點都做不到；行政院公報只有 Title + 文件性質分類（非議題分類），沒有全文欄位可挖，且只有「今天」的資料，無法支撐跨年份的歷史敘事。**駁回理由（原則面）**：共筆自己驗證過 LYAPI 中文檢索是字元級模糊比對（「解凍」配到「解釋」），關鍵字聲量統計已被專案自己標記為不可信；議題語意分類跟企劃案 1.1 節的法定分類（法律案/預算案）是不同維度，混用會製造新的誤讀。

### C. UX「記憶迭代」用於使用者個人化
**駁回理由**：直接牴觸共筆〈不做個人化推薦〉與企劃案 3.5 節「系統不自動推薦要看哪條」；且會破壞「同一網址任何人打開結果一致」這個支撐 NGO 研究員/研究生兩種核心受眾的可引用性要求。**保留的部分**：純介面偏好記憶（不涉及內容選擇，如白話/專業模式切換）不算個人化推薦，可以做，已納入 Phase 2 範圍。

### D. 議題層級的「記憶迭代」（學習典型進度模式，跨議題比較速度/標記異常）
**駁回理由**：即使不是針對個人，這種「記住類別典型耗時、拿新案子比對標記異常」的做法，直接落入企劃案 2.4 節禁止清單「不計算『平均耗時』之類的聚合統計去暗示效率高低」——因為對讀者而言，「這條線比同類案子慢」跟「這條線比較沒效率」是同一句話。**保留的部分**：議題對自己過去狀態的記憶（`days_since_anchor`、`days_since_prev`，不跟其他議題比較）已經在 `fetch_lyapi.py` 實作，這個沒問題。

### E. 用歷史修正紀錄迭代改善跨案自動串連（active learning）
這是唯一沒有被駁回、進一步展開規格的方向，見 `spec/candidate_linker.md`。**採用的前提條件**：掃描範圍限定在已追蹤線的鄰域、不自動發布、必須有熔斷機制防止候選佇列無限累積、優先用結構化欄位（對照表法條重疊）而非文字關鍵字模糊比對當主要訊號。

## 8. 已知會撞到的維護成本天花板

共筆自訂死亡條款：「維護成本連續兩季超過每季 4 小時」即公開結案。上述所有 Phase 疊加後的持續性人力成本（選線把關隨線數線性增加、屆期不連續的週期性重新串接、候選清單複核）很可能超過這個自訂上限，除非刻意壓低開新線的頻率（例如一年 1～2 條）。這不是這份文件能解決的問題，是坑主需要在啟動 Phase 1 前先想清楚的權衡，實作者不應該假設人力會自動跟上功能擴張的速度。
